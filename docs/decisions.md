# 設計判断ログ

要件の詰め（grillingセッション, 2026-08-14）で確定した決定事項。

## 確定済み

### D1. 実行環境は社用PC（Windows）、開発はMac
- 社用PC: Windows / Outlookデスクトップアプリ / Python・Node導入可 / AIは **GitHub Copilot**
- 開発機（Mac）にはOutlook・O365が無い。**Mac上では実行検証ができない**
- → Macでは「叩き台」を書き、動作確認は社用PCで行う前提

### D2. Outlookは「クラシック」
- 新しいOutlook（Webアプリ版）ではなくクラシック版
- → **pywin32 のCOM自動化**が使える。Entra IDのアプリ登録・管理者承認・認証すべて不要
- ただしMicrosoftは新しいOutlookへの移行を進めているため、**Outlook操作は差し替え可能なアダプタ層に隔離**する（D3）

### D3. Outlook操作はアダプタ層に隔離する
- `adapters/base.py` に抽象インタフェースを定義し、業務ロジックはそこにだけ依存する
- 現在の実装は `adapters/com_outlook.py`（pywin32 / クラシックOutlook）
- 将来「新しいOutlook」に移行したら `adapters/graph_outlook.py` を追加するだけで済む構成にする

### D4. スキルは Agent Skills 標準形式で書く
- `SKILL.md`（YAMLフロントマター + Markdown本文）+ スクリプト同梱、というAgent Skillsの形式は
  **GitHub Copilot（VS Code / CLI / coding agent）と Claude Code の両方が読む**オープン標準
- → 社用PCがCopilotでも、同じスキル資産がそのまま使える
- 配置先ディレクトリ（`.github/skills/` と `.claude/skills/` の扱い）は**保留**

### D5. 予定の仮抑えは「自分の枠をTentativeで押さえる」
- `.ics`ファイル生成止まりではなく、実際にカレンダーへ仮予定を作る
- 出席者への招待送信は**この時点では行わない**
- 確認後に招待を送るフローへ昇格させる（承認の具体的な形は**保留**）

### D6. メール下書きは自分の過去メールの文体を模倣する
- 過去の自分の送信メールを数件参照し、同じ雰囲気で下書きを生成する
- **メールの自動送信は一切しない。下書き保存止まりを固定制約とする**

### D7. プロジェクトは独立リポジトリとして `~/Git/outlook-assistant`
- `dellgreen-company` の配下ではなく、`~/Git/` 直下に独立して作る
- 周囲の慣習（1プロジェクト＝1リポジトリ、kebab-case）に合わせた
- GitHubへのpush有無は**保留**（未実施）

### D8. 業務データはリポジトリで管理しない
- 抽出した過去メール本文、連絡先、予定の実データはすべて `.gitignore` で除外
- リポジトリにはコード・テンプレート・サンプル（`*.example.*`）のみ置く
- 本人確認済み（「そもそもメールとかはプロジェクトで管理する気はない」）
- privateリポジトリでもGitHubは社外サービスであるため、業務メール本文を載せる構図を避ける

### D9. 承認は「コマンド2本の分離」で表現する
- `hold` … 自分の枠だけTentativeで押さえ、予定IDを表示して終了。**招待は送らない**
- `invite --id <ID>` … 内容を確認した後で、出席者へ招待を送る
- 1と2の間に時間が空いてよい（翌日でもよい）
- 理由: 「問題ないことを確認できたら送りたい」という要件は、確認と送信の間に時間が空くことを含む。
  その場で y/N を迫る方式だと、実質的な確認が挟まらない
- **この分離自体が承認の仕組みなので、`invite` に確認プロンプトを足さないこと**（承認が二重になり形骸化する）

### D10. 出席者の空き時間を確認し、全員が空いている枠を出す
- `Recipient.FreeBusy` を使う。**Outlookのスケジュールアシスタントと同じ経路**なので、
  追加の権限申請もアプリ登録も不要。逆に、あの画面で見えない相手はここでも見えない
- 誰か一人でも埋まっていればその時間は候補から外す
- **照会に失敗した相手がいても処理を止めず、「誰が未確認か」を必ず返して表示する。**
  空き時間情報を公開していない相手は「空き」ではなく「不明」であり、
  これを黙って混ぜると誤った候補を送ってしまうため
- 仮の予定（FreeBusyの `1`）も「埋まっている」扱いにする。仮でも先約は先約なので
- 候補は業務時間（既定9-18時）に絞る

### D11. 文体は送信済みメールから自動抽出してプロファイル化する
- `style` コマンドで送信済みアイテムの直近N件を読み、**文体プロファイル**を生成する
- 抽出するのは機械的に観測できる要素だけ: 書き出し・結び・署名・1行の平均文字数・
  段落を空行で区切るか・敬語表現の量
- **文章の生成はPython側でやらない。** 「その人がどう書いてきたか」を観測可能な形にするのがここの仕事で、
  「どう書くか」はAIエージェントの仕事
- 返信・転送の引用部分は落としてから統計を取る（相手の文体を自分の癖として学習しないため）
- 署名は「全メール共通の末尾ブロック」として検出し、書き出し・結びの統計から除外する
- 出力先は `data/style_profile.md`（`.gitignore` 対象）。本文をまるごと保存せず定型部分と統計値に
  落とすのも、業務メールをファイルに残さないため
